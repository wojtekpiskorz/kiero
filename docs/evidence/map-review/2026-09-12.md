## Standards review

These are concrete breaches of the documented deletion contract, not code-smell preferences. I4 requires tombstone checks before derived publication and says late AI/push results must not expose deleted sources. See `docs/implementation/issues.json:2086` and `:2091`.

### S1. P1: queued push can send deleted source text

`convex/operations/deletion/executor.ts:215` suppresses only `pending` and `evaluating` notification intents. An intent already marked `delivered` by F2 and its pending per-device delivery survive. On retry, `convex/attention/push/operations.ts:398` reuses the delivery's old `payloadJson`; `convex/attention/push/functions.ts:217` sends that payload. The payload can contain the original message preview.

Trigger: prepare a delivery, leave the transport pending, permanently delete its source, then retry delivery. The retry can send the preserved preview. This is not merely the unavoidable interval around a request already sent before deletion.

Repair: invalidate affected delivery work and redact stored payloads as part of deletion handling; recheck the current source lifecycle before transport authorization. Add a prepare-delete-retry regression. The existing retry test at `tests/f3/push.test.ts:447` covers row reuse, not source deletion between attempts.

### S2. P1: clarification content and late agent work survive deletion

I4 deletes fragments and extraction rows at `convex/operations/deletion/executor.ts:153`, but does not handle `clarifications`. `convex/memory/findings/exposition.ts:233` still exposes `question` and `resolutionNote` when their conflicting fragments have disappeared. A question quoting a deleted message can therefore remain visible after purge stages finish.

There is also an in-flight path: `convex/agent/execute.ts:69` and `convex/memory/findings/corrections.ts:159` check source existence/company but not active lifecycle. A late tool can create a clarification after the source is tombstoned and before fragments are deleted. `stalenessRecheck` at `convex/agent/execute.ts:302` aborts only for a missing row, while I4 retains a tombstone.

Repair: handle existing clarification content before destroying its source associations, preserving valid independent evidence where applicable; enforce current active-source checks at agent writes and final checks. Cover both existing and in-flight clarifications. The reviewer ran the existing focused E6/I4 suite, 56 passing tests, but these interleavings are absent. These findings are supported by static end-to-end code traces, not a new live reproduction.

## Spec review

### P1. P1: clarification resolution drops new evidence

E6 [#40](https://github.com/wojtekpiskorz/kiero/issues/40) requires resolution with a new source-backed response. `packages/agent/tools/tools.ts:129` requires `evidenceIds`, but `convex/agent/loop.ts:352` drops them when dispatching. `convex/agent/execute.ts:162` forwards only the clarification and note, and `convex/memory/findings/corrections.ts:228` persists resolved state, note, actor and time. No association to the new source is stored.

Trigger: resolve a clarification using new evidence, then inspect its persisted history. The resolution has no traceable new basis, preventing source-aware withdrawal, recomputation and audit.

Repair: pass validated source/fragment references through the command and persist them atomically with the resolution. Test both preservation of the references and later source withdrawal. This finding does not assume every clarification resolution must rewrite an unrelated finding.

### P2. P1: stale reassignment overwrites another boss's project links

E7 [#115](https://github.com/wojtekpiskorz/kiero/issues/115) requires refusal of stale input. `packages/contracts/src/modules/sources.ts:81` accepts only a source and complete replacement project set. `convex/sources/reassign/reassignment.ts:224` reads the current set, but `:243` replaces it without a client-observed version precondition. The form snapshots initial selection at `apps/web/src/features/source-detail/reassign.ts:40`.

Trigger: A and B open a source assigned to P1. A moves it to P2. B submits the old form with P1+P3. The command silently removes A's P2 and starts scope reassessment from B's replacement.

Repair: add a placement revision or expected-current-set precondition, checked atomically; inform the stale editor and reload its selection. Test two independently loaded forms. Database transaction serialization alone does not detect stale user intent.

### P3. P2: evidence links cannot open sufficiently old sources

H1/H3 promise stable source links. `apps/web/src/features/memory/MemoryFeature.ts:311` and equivalent search/Co teraz links point to `/?zrodlo=<id>`. Conversation detail only renders for a source already present in the loaded feed at `apps/web/src/features/conversation/ConversationFeature.ts:447`. That feed starts at 30 and caps at 120; the load control disappears at `:332`.

Trigger: follow a memory/search evidence link after more than 120 newer messages. The target source cannot enter the feed, so its detail never opens.

Repair: use the direct `/zrodlo?zrodlo=<id>` dossier consistently or fetch the selected source independently of feed pagination. Test an old source beyond the cap.

### P4. P1: Release workflow calls a nonexistent entry point

`.github/workflows/release.yml:94` and `:144` call `infra/release/verify-release-target.mjs`. The committed file is `infra/release/verify-target.mjs`.

The exact staging command was executed locally and exited 1 with `MODULE_NOT_FOUND`. Calling the actual file succeeded. The migration rehearsal independently passed 9/9 rows, so that result does not validate the workflow entry point.

Repair the reference and run the command used by the workflow in a test. Current release tests import the correctly named module and inspect YAML strings, which misses the broken executable path.

### P5. P1: release implementation stops at placeholder deployment steps

I7 [#59](https://github.com/wojtekpiskorz/kiero/issues/59) explicitly requires a workflow that deploys isolated synthetic staging. Even when the provisioning secret exists, `.github/workflows/release.yml:107` and `:157` only execute `echo`. There is no web build/deploy, Convex deployment or Worker deployment in these jobs. Provisioning credentials alone will not complete this feature.

GitHub currently has no configured environments, so the YAML `environment: alpha-production` is not evidence that a protected approval environment already exists. The workflow also records rehearsal evidence without a deployment outcome.

Repair: implement and prove real staging deployment, configure environment protection, and distinguish a rehearsal, a blocked deployment and a completed deployment in evidence. Keep production activation outside this review's scope. This work should be a concrete prerequisite to the release/device qualification in J4.

Standards: 2 findings, worst severity P1. Spec: 5 findings, worst severity P1. No broad maintainability rewrite is recommended from this bounded review.
