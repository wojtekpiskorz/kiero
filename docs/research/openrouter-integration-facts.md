## TanStack AI

TanStack has an official `@tanstack/ai-openrouter` adapter. Its upstream documentation exposes `openRouterText` for Chat Completions and `openRouterResponsesText` for the Responses-shaped protocol. The former is described as the stable default; the latter is beta. Tools and structured output support depends on model capabilities, and fallback models can affect whether one or two upstream calls are used. Reported request cost is forwarded when available; absent cost is not zero. These are current documentation/source observations, not proof that a particular published package version supports the entire example. [Adapter documentation](https://tanstack.com/ai/latest/docs/adapters/openrouter), [upstream source](https://github.com/TanStack/ai/blob/main/docs/adapters/openrouter.md)

Implementation direction under the owner's simplification instruction: use the dedicated Chat Completions adapter with a server-held application key. Preserve Kiero's Convex-owned source history and Effect validation. Do not copy example model names, Zod usage or unvalidated browser input into Kiero as accepted design choices. Exact package compatibility remains part of the existing stack proof.

## Logging and routing

OpenRouter states that prompt/response retention is opt-in. Private input/output logging and permission for OpenRouter to use input/output content are separately disabled by default. It still records request metadata such as token counts and latency and describes anonymous categorization. Do not turn this into a claim that no processing or metadata storage occurs. [Data collection](https://openrouter.ai/docs/guides/privacy/data-collection)

Upstream providers have their own policies. OpenRouter exposes separate training-routing preferences for paid/free models. Opting out of training excludes providers classified as training on requests; this differs from OpenRouter's own opt-ins and from each provider's retention. The documentation's policy classification is not a complete independent audit of providers. [Provider logging](https://openrouter.ai/docs/guides/privacy/provider-logging)

Chat routing supports `require_parameters: true`, which excludes providers that do not support all requested parameters. Without it some parameters may be ignored. Provider order and allowlists control endpoint selection; `data_collection` controls data-policy filtering, while `zdr` separately restricts routing to endpoints classified as zero-retention. These are different controls. The routing docs' descriptions of storage/training overlap; do not equate a no-training preference with proved zero retention or a particular number of retention days. [Provider selection](https://openrouter.ai/docs/guides/routing/provider-selection)

Routine alpha direction: leave optional full payload logging and input/output reuse off, retain a no-training routing preference where available, and do not add tester-facing configuration or compulsory training consent. The owner deferred formal legal/provider-retention discussion. No setting is represented as legal compliance, and no live account setting was changed.

## Speech-to-text

OpenRouter now documents a dedicated `/api/v1/audio/transcriptions` endpoint. It accepts base64 JSON and OpenAI-compatible multipart. Multipart is limited to 25 MB; larger JSON uploads and streaming offload are described, without establishing unlimited per-request processing. The guide warns about upstream 60-second processing timeouts and recommends splitting long jobs. `verbose_json` and requested segment/word timestamps are supported only for qualifying models/providers; unsupported combinations can return 400. General multipart `prompt` is accepted but ignored, while provider-specific options have different forwarding rules. The guide explicitly says `provider.order`, `only` and `ignore` are not applied to transcription requests. Do not infer that every chat routing/filter parameter applies here. [STT guide](https://openrouter.ai/docs/guides/overview/multimodal/stt)

OpenRouter is the first STT integration to evaluate under the chosen gateway. Preserve the no-product-duration-cap contract by segmenting processing and maintaining one source with original-time anchors. Use one chosen, tested route rather than assuming every advertised STT model returns the required timestamps. A separate ElevenLabs integration is not automatically required, selected or ruled out if later evidence demonstrates a need.
