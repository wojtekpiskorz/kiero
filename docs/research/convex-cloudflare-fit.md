# Convex and a Cloudflare frontend: fit notes for Kiero

**Status: 8 September 2026.** This is upstream research, not a backend choice or a tested integration. Locally, Kiero has no `package.json` or lockfile, so no Convex version or Effect/Convex compatibility contract exists yet. It is read alongside `architecture-backend-facts.md` and `architecture-typed-foundations.md`: Kiero needs one canonical, auditable source/journal graph, atomic current-state plus provenance writes, checked domain operations for UI and AI, tenant isolation, immediate cut-off of new reads/writes/push after membership revocation, EU-resident persistent data/files/backups, and asynchronous long media.

## Documented Convex facts

* A Vite React client can create `ConvexReactClient` from `import.meta.env.VITE_CONVEX_URL`, wrap the tree in `ConvexProvider`, and call generated API references through `useQuery`/`useMutation`. `useQuery` subscribes and re-renders when its query result changes. This is a hosted Convex backend reached by URL; it does **not** require the React/Vite frontend to run on Convex. A Cloudflare-hosted static frontend is therefore a plausible separate client deployment, but URL, CSP, auth-token and failure-mode integration still need a small proof. [React overview](https://docs.convex.dev/client/react/overview) · [Vite deployment URL](https://docs.convex.dev/client/react/deployment-urls)

* Convex’s schema and `v` validators validate documents/function arguments at runtime and drive generated `Doc`, `Id`, function-context and client API types. This is a strong single-platform boundary. It is not the same vocabulary as Effect 4 `Schema`: using Effect for domain commands, errors and parsing is plausible TypeScript composition, but this research found no tested or documented Effect-4-RC-to-Convex validator bridge. Keep Convex validators at the persistence/public-function boundary unless a pinned-version spike proves a safe adapter. [Convex TypeScript and validators](https://docs.convex.dev/understanding/best-practices/typescript)

* Queries and mutations run in Convex’s custom JavaScript runtime; actions default there too (browser-like API, no cold starts). Only actions can opt into Node using a file-level `"use node"`; Node files cannot contain queries/mutations and must use `runQuery`/`runMutation` to touch data. This informs where Effect packages and model SDK dependencies can execute; package compatibility must be verified after pinning versions. [Runtimes](https://docs.convex.dev/functions/runtimes)

* Scheduling from a mutation is atomic with that mutation. Scheduled mutations execute exactly once with automatic transient-error retries; scheduled actions execute at most once and are not automatically retried because external effects may already have happened. Convex’s Workflow component is documented as durable, restart-surviving multi-step execution with recorded step results, configurable retries and delays. It can reduce queue plumbing, but external LLM/push calls still need idempotency keys, an outcome record, and conditional domain publication. [Scheduled functions](https://docs.convex.dev/scheduling/scheduled-functions) · [Workflows](https://docs.convex.dev/agents/workflows)

* Convex offers US East and **EU West (Ireland)**; all deployment infrastructure is hosted in the selected region. A deployment cannot change region; the documented move is export/import into a new deployment. This supports an EU-region selection, but is not by itself a complete legal/data-processing assessment. The backup documentation does not separately state the geographic location of retained/downloaded backups, so EU backup residency needs contract/support confirmation. [Regions](https://docs.convex.dev/production/regions)

* A backup is a consistent snapshot of table data and optionally Convex file storage. Its downloadable ZIP contains table JSONL and, when selected, files plus `_storage` metadata. It excludes code/configuration, environment variables/secrets and pending scheduled functions. Periodic daily/weekly backups require Professional; the current official floor states Professional is **$25 per developer/month**. Do not map this to Kiero’s 500 PLN alert without measured storage, egress, function and model workload. [Backup and restore](https://docs.convex.dev/database/backup-restore) · [Pricing](https://www.convex.dev/pricing)

* `storage.getUrl()` creates a bearer URL: anyone holding it can read the file, and deletion is the only documented revocation. An HTTP action can recheck authorization but has a 20 MB response limit. Convex itself suggests its Cloudflare R2 component for expiring URLs; that recommendation is evidence of an available integration path, not evidence that it satisfies Kiero’s immediate membership-revocation or long-voice requirements. Validate its signing/expiry/revocation semantics directly before relying on it. [File storage security model](https://docs.convex.dev/file-storage/overview)

## Fit considerations (inference)

Convex is a credible fit where Kiero values live shared conversation/current-state views and wants to avoid building subscription sync and basic scheduling. The relational source graph is not evidence that Convex is incapable: separate document tables, IDs, indexes and transactional mutations can model it. The trade-off is implementation ergonomics: PostgreSQL expresses joins, constraints and ad-hoc relational inspection more directly, while Convex requires deliberately shaped queries and application-level invariants.

Either backend needs a domain mutation that atomically writes source/journal/current-state and rechecks tenant membership before every client query, command, scheduled continuation and push decision. Scheduler auth is not propagated, so a stored user ID is not authorization. Existing bearer file URLs cannot meet immediate access cut-off without deletion/re-upload; use an authorization-checked or expiry-based serving design. Treat long voice notes as asynchronous object-storage/processing work and measure real file/transport limits before promising no product cap.

**Upstream source-code observations:** none; all claims above come from current official documentation. A decision-ready spike should pin Convex and Effect 4 RC versions, exercise a React/Cloudflare deployment, membership revocation during subscriptions/jobs/file access, and crash points before/after an external model call and before conditional publication.

## Follow-up: boundaries for a Convex-first evaluation

The owner subsequently approved evaluating Convex as the primary candidate. This does not establish runtime compatibility or change the research claims above.

Convex mutations read a consistent database view and commit their writes together. Queries and mutations must be deterministic and cannot call external APIs. Actions can call those APIs, then invoke mutations, but an action's earlier read and later mutation do not share one transaction. Kiero's conditional-publication mutation must recheck the relevant access, source and entity revisions and write current state, provenance and history together. The previously accepted autonomous-AI behavior remains; this is server validation, not a new human approval step. [Mutation transactions](https://docs.convex.dev/functions/mutation-functions) [Actions](https://docs.convex.dev/functions/actions)

Native validators cover stored data and function inputs/outputs and produce TypeScript types. Schema deployment checks existing documents, and incompatible data can block the deployment. Schema enforcement does not populate missing values. A migration proposal should use compatible intermediate shapes, bounded backfill, verification and subsequent narrowing. Exact APIs and limits must be checked against pinned versions. [Validation](https://docs.convex.dev/functions/validation) [Schemas](https://docs.convex.dev/database/schemas)

The documented TanStack Query adapter supplies ConvexQueryClient and convexQuery for reactive query results. It is beta and does not expose every feature of the native Convex React client. This supports evaluating the accepted Router/Query frontend without silently replacing its libraries; loading, pagination, authentication changes and reconnect need explicit checks. [TanStack Query adapter](https://docs.convex.dev/client/tanstack/tanstack-query)

The Workflow component records step results and resumes incomplete work with configurable retries and delays. An external action still needs safe retry/outcome handling. The proposed durable owner is Convex; Effect can execute the domain and integration logic inside its invocation boundaries. [Workflow documentation](https://docs.convex.dev/agents/workflows)

A delegated inspection of current upstream Workflow client source found a start path callable with mutation or action context that invokes an internal mutation. This is an upstream-main observation, not evidence for an installed version. The selected-version proof must demonstrate that source acceptance and durable workflow registration commit together when started from a mutation; starting from an action does not make an earlier provider call transactional. [Workflow client source](https://raw.githubusercontent.com/get-convex/workflow/main/src/client/index.ts)

Design implications remain proposals: separate growing conversations, sources, provenance and history into bounded linked documents; load indexed pages instead of an entire firm's graph; group mutually dependent domain changes in a single mutation; track partially completed independent groups against one immutable source. Do not describe any of these as a schema already implemented in Kiero.

## Follow-up: retrieval and current records

Convex text search runs as a reactive, consistent transactional query. Its indexes support equality filter fields. It uses token/prefix matching; exact ranking can change and this documentation does not prove Polish construction-domain retrieval quality. Kiero should require the authorized firm filter inside the search expression. [Text search](https://docs.convex.dev/search/text-search)

Vector indexes are current with stored vectors, but vector search runs only in actions and returns IDs and scores. Records may change or disappear before subsequent hydration; vector candidates are not reactive query results. Indexed filter fields support restricting retrieval before result loading. Embedding creation and refresh remain application work. Kiero should authorize the search scope, then hydrate and recheck records before use. Stale embedding payloads and action/query races must not be confused with an eventually consistent native vector index. [Vector search](https://docs.convex.dev/search/vector-search)

Design implication: structured current-state reads answer deterministic operational questions. Text and semantic retrieval discover relevant records and source fragments, whose current state and permissions are then checked. A similarity score is not confidence that a business fact is true. Candidate selection must preserve the distinction between historical evidence and current agreement. Embedding provider, dimensions, chunk boundaries, refresh cost and actual relevance still require selection and a representative test. No retrieval implementation or quality measurement was performed.
