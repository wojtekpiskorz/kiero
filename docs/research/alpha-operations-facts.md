# Alpha operations facts and candidates

Checked on 2026-09-08. The existing one-hour recovery-point and eight-hour recovery-time targets are accepted requirements. The owner subsequently accepted the complete Q201–Q204 round: EU Cloudflare Container export every 15 minutes, protected R2 backups, frequent copies for 48 hours and daily copies through day 14, authenticated 24-hour firm exports, and Axiom diagnostics/owner alerts. Historical proposal wording below records that accepted direction. No service, schedule, account, paid plan or deployment has been created, and no recovery or alerting proof has run.

## Backup execution

Convex documents `convex export --path snapshot.zip`, optional Convex file storage and explicit production/deployment selection. An export covers the deployment, not a company-scoped user download. External R2 media need separate protection and manifest reconciliation. The earlier [recovery report](backup-recovery-facts.md) records snapshot consistency, excluded code/secrets/scheduled work and restore constraints. [CLI export](https://docs.convex.dev/cli/reference/export)

Cloudflare documents starting a container from a Workers Cron Trigger. It also documents container placement constraints, including `jurisdiction: eu`. This provides a candidate Linux runtime for the pinned Convex CLI without moving Kiero's canonical domain workflows out of Convex. It does not establish a successful Kiero export or guarantee that every scheduled start completes on time. The container's working files must be treated as temporary; checkpoints and verified outputs belong in durable storage. [Cron Container](https://developers.cloudflare.com/containers/examples/cron/), [jurisdictional placement](https://developers.cloudflare.com/changelog/post/2026-04-05-regional-placement/)

Proposed Q201: run a dedicated backup container in the EU every 15 minutes, using the documented CLI, explicit deployment identity and a pinned runtime. Store full database snapshots, media manifests and protected copies of referenced R2 objects in a separate private R2 EU backup bucket with separate credentials. Application media cleanup must not possess backup deletion authority. A completed set requires verification of every referenced object, including component/auth/workflow state needed for restoration. A start, downloaded ZIP or media list alone does not prove recoverability. Measure age from the represented snapshot time, not job completion. Alert before the age reaches one hour. Make overlapping, interrupted and stale job attempts safe, with temporary-file cleanup and a durable completion marker.

This choice protects against a class of application/storage deletion mistakes. A second bucket on the same provider is not independent of a Cloudflare-wide or account-wide incident. The existing recovery drill must state coverage and actual restoration constraints. No multi-provider disaster recovery is silently promised. Native Convex backups remain supplemental where available; their region/retention must meet the already accepted policy.

Proposed Q202: retain all complete 15-minute recovery sets for 48 hours, then one complete set per day through day 14. Media copies remain while referenced by retained sets; do not blindly expire a still-needed object by its original upload age. Enforce the accepted deletion-specific maximum of 30 days without extending it through backup copying. Prune manifests and unreferenced media together. The external content-free deletion/revocation ledger is not rolled back with the application database and must remain available until every relevant recovery set has expired or been sanitized.

Render was also checked as an alternative, not selected. Its managed cron jobs support Frankfurt, one active run per job, delayed scheduled overlap, manual-trigger cancellation of the current run, a 12-hour run ceiling and per-second billing with a $1 monthly minimum. Cloudflare is proposed first to keep this execution capability within the existing hosting provider. No claim is made that either candidate has passed the recovery target. [Render cron jobs](https://render.com/docs/cronjobs), [Render regions](https://render.com/docs/regions)

## Firm export behavior

Proposed Q203: an administrator requests an asynchronous firm export containing a readable HTML index, versioned JSON data and retained media. It includes the accepted current state, history, source references and extension definitions, with the accepted optimized-photo exception. The archive describes a consistent firm state at a recorded time; later ordinary updates appear in a subsequent export. A full deployment backup, credentials, sessions or another firm's records must never reach this download.

Use a private temporary archive available for 24 hours after completion. Recheck current administrator rights at creation, publication and download/range access. A later permanent source deletion must immediately invalidate any downloadable archive containing that source, even if its original snapshot predates deletion; background bytes follow the existing live-purge deadline. Generate a fresh archive on request. Escape source text in HTML, use safe media filenames and relative paths, and verify the archive after extraction. The implementation must prove consistent pagination/snapshot assembly and tenant isolation; paginating changing live tables is not a snapshot algorithm. Download uses the existing authenticated streaming boundary, not a public bearer URL.

## Observability

Convex Pro supports log streams to Axiom and other destinations. Delivery is best effort: events may be dropped or duplicated. These streams cannot replace Kiero's durable domain history or be the sole proof that every source was processed. [Convex log streams](https://docs.convex.dev/production/integrations/log-streams)

Cloudflare documents export of Workers logs and traces to Axiom over OpenTelemetry. Native Workers Logs retain three days on Free and seven days on Paid, so native logs alone do not provide the accepted 30-day diagnostic window. [Axiom export](https://developers.cloudflare.com/workers/observability/exporting-opentelemetry-data/axiom/), [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)

Axiom allows dataset-specific retention; Personal defaults to 30 days. Retention and the permitted query window are separate. Dataset trimming operates on storage blocks, so an advertised setting is not evidence of exact per-event physical deletion at a boundary. Verify the configured plan, retention behavior and query availability before claiming the complete diagnostic requirement. [Dataset retention](https://axiom.co/docs/reference/datasets)

Proposed Q204: Axiom for redacted technical logs, latency and cost events across Convex, Workers and the backup job, with the accepted 30-day policy. Keep source content in protected Kiero records and preserve audited GM drill-down. Configure alerts to the owner for stuck processing, failed media acceptance, backup freshness and existing cost thresholds. Include missing heartbeat detection outside Convex so total backend silence is actionable. Axiom documents threshold monitors and email notification delivery; exact quotas, monitor cadence, account plan and external probe need proof. This is an architecture proposal, not authorization to send a message now. [Monitors and notification delivery](https://axiom.co/docs/monitor-data/monitors)

Before enabling automatic logging, inspect default request URLs, headers, exception fields and SDK instrumentation. Prefer explicit allowed fields and redact before external ingestion; disabling optional AI payload logging alone does not sanitize an exception. Do not enable session replay or full prompt capture as a side effect of selecting a monitoring provider.
